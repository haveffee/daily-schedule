# Подготовка подписок HVF

Сейчас приём денег **выключен**. Владелец пока физическое лицо без договора эквайринга. Все возможности приложения остаются доступны в бесплатной бете. Здесь подготовлен закрытый серверный адаптер bePaid; это не подключённая касса и не подтверждение допуска к продажам.

Утверждённые тарифы: **8 BYN за месяц** или **72 BYN за год**. Сервер хранит цены в копейках: 800 и 7200. Годовой план bePaid задаётся как 12 месяцев. Клиент передаёт только `monthly` или `yearly`; сумма, валюта, пользователь и период не принимаются от браузера.

## Подключение к приложению

```js
import { createBilling } from '../billing/worker.mjs';
const billing = createBilling();
// В основном Worker, для путей /api/billing/*:
return billing.fetch(request, env);
```

Адаптер использует изолированное D1-подключение `BILLING_DB`. Таблицы создаются миграцией `migrations/0001_billing.sql`. Они содержат UID аккаунта, серверный заказ, тариф, идентификатор подписки у провайдера, оплаченный срок и журнал обработанных событий. Реквизиты карт, дела, доходы и траты сюда не передаются.

Тесты: `node --test tests/backend-billing.test.cjs`. Они запускают настоящие SQL-миграции в SQLite и создают настоящие RSA-подписи. Платёжная сеть заменена контролируемым транспортом; настоящих списаний тесты не делают.

## Контракт API

Все ответы JSON с `Cache-Control: no-store`. Ошибки: `{ "error": { "code": "...", "message": "..." } }`.

| Путь | Доступ и результат |
| --- | --- |
| `GET /api/billing/catalog` | Публичный каталог `{mode, paymentsReady, currency:'BYN', plans, message}`. `amount` в копейках. |
| `GET /api/billing/status` | Firebase Bearer ID token. `{mode,paymentsReady,plan,status,periodEnd,renewAt,billingPlan,cancelAtPeriodEnd}`. Даты ISO или `null`. |
| `POST /api/billing/checkout` | Firebase Bearer ID token, JSON `{plan:'monthly'|'yearly'}`. Возвращает `{checkoutUrl,orderId}`. |
| `POST /api/billing/cancel` | Firebase Bearer ID token, JSON `{}`. Отменяет продление только своей подписки; `{canceled:true,periodEnd}`. |
| `POST /api/billing/webhook` | Авторизация магазина и RSA-подпись bePaid по исходным байтам JSON. Данные браузера не заменяют уведомление. |

В выключенном режиме каталог сообщает `mode:'disabled'`, `paymentsReady:false`; статус авторизованного пользователя — `plan:'free'`, `status:'beta'`. Checkout, отмена и webhook возвращают 503 с понятным сообщением. Записи в D1 и запросы к bePaid не выполняются. Проверка Firebase-токена может обращаться к публичным ключам Google.

В рабочем режиме `plan` равен `free` или `plus`; `status` — `free`, `pending`, `active`, `canceled` или `expired`. После отмены сохраняется только уже подтверждённый оплаченный срок. Установка флага в localStorage, возврат с платёжной страницы, тестовый платёж или один лишь `state:'active'` из присланного JSON не дают Plus.

## Почему сейчас нельзя просто включить списания

Для bePaid нужны одобрение продавца/его деятельности, договор и банковские реквизиты. bePaid сообщает, что работает и с самозанятыми, но конкретные способы оплаты для них согласуются индивидуально. Нельзя считать, что физическому лицу уже разрешены автоматические подписки.

Кроме того, опубликованные требования bePaid к сайту предусматривают собственный домен, регистрацию БелГИЭ и размещение сервера в Беларуси; бесплатные серверы не допускаются. Поэтому бесплатный адрес Cloudflare подходит для текущей беты, но его нельзя автоматически считать согласованным продающим ресурсом. Сначала нужно согласовать архитектуру с bePaid или подобрать подходящее размещение. Никакие заявки или сообщения от имени владельца этим кодом не отправляются.

## Подготовка к настоящему подключению

1. Оформить допустимый для продавца статус и получить подтверждение bePaid для SaaS-подписок, размещения сайта и выбранной деятельности. Подготовить реальные реквизиты продавца, контакты, условия оплаты, продления, отмены и возврата. Не публиковать выдуманные реквизиты.
2. Пройти тестирование в отдельном стенде и отдельной базе. Проверить оплату, повторное списание, отказ, истёкшую карту, отмену, возврат и спорный платёж с провайдером. Этот адаптер намеренно не включает публичный тестовый checkout: тестовые планы никогда не открывают живой Plus.
3. До активации дополнить согласованную с провайдером сверку возвратов/чарджбэков и операционное восстановление неоднозначных заказов. Текущий endpoint обслуживает уведомления **подписок**; он не заменяет обработку всех возможных уведомлений о транзакциях. Реального испытания магазина пока не было.
4. После тестирования создать в bePaid два настоящих плана без trial: BYN 800/1 month и BYN 7200/12 months, с `test:false`. Адаптер проверяет содержимое плана перед созданием checkout.
5. Применить миграцию к изолированному `BILLING_DB`. Настроить HTTPS `APP_URL` с origin приложения; return URL и webhook строятся сервером. Не использовать пользовательские callback URL.
6. Установить секреты через защищённый механизм хостинга: `BEPAID_SHOP_ID`, `BEPAID_SECRET_KEY`, `BEPAID_MONTHLY_PLAN_ID`, `BEPAID_YEARLY_PLAN_ID`, `BEPAID_WEBHOOK_PUBLIC_KEY` (PEM SPKI). Не помещать секрет в публичные JS-файлы, git или клиентский конфиг.
7. Только после выполнения предыдущих пунктов установить `BILLING_MERCHANT_APPROVED='true'` и `BILLING_MODE='live'`. Наличие флагов само по себе не является договором или одобрением провайдера. По умолчанию оставлять `BILLING_MODE='disabled'`.

Неполная конфигурация всегда возвращает выключенный режим. Секреты не выводятся в API. Размещение этого кода на сервере с `disabled` не проводит платежи и не начинает подписку владельцу или клиентам.

## Проверка платежей и ограничения адаптера

Запросы к фиксированному `https://api.bepaid.by` используют Basic-авторизацию и `redirect:'manual'`, тайм-аут 12 секунд, ограниченный JSON-ответ. Клиент уходит только на HTTPS-страницу `checkout.bepaid.by/v2/`. Подписка создаётся для серверного заказа и проверенного тарифного ID.

Подтверждённое уведомление повторно читает актуальную подписку из API провайдера. Проверяются серверный `tracking_id`, ID подписки и плана, BYN, сумма, интервал, `test:false`, успешная транзакция, число оплаченных циклов и разумная граница оплаченного периода. Подпись RSA/SHA256 проверяется по исходному телу без повторной сериализации. Хэш тела защищает от повторной обработки; версия записи защищает от конфликтующих обновлений. Устаревший webhook не используется как источник текущего состояния.

Одновременные checkout ограничивает уникальный SQL-индекс на активный/ожидающий заказ аккаунта. Повторное нажатие возвращает уже созданную страницу того же тарифа. Нельзя открыть новую оплату поверх подтверждённого оплаченного периода.

При неоднозначном тайм-ауте создания заказ остаётся `creating`, а повторный checkout блокируется. Это сознательное поведение: bePaid документирует `RequestID`-идемпотентность только для карточных/альтернативных транзакций, не для создания подписки. Перед ручным разрешением такого заказа нужно проверить кабинет/API провайдера и убедиться, что скрытая действующая подписка не существует. Автоматически удалять этот блокирующий заказ или повторять POST создания нельзя.

Не предусмотрены изменение тарифа посреди периода, пропорциональный перерасчёт или сбор карточных реквизитов собственным интерфейсом. Базовые функции текущей беты не блокируются. Для дальнейших платных серверных функций проверка доступа должна выполняться на сервере по подтверждённому периоду, а не только скрывать кнопку в клиенте.
